# سیاست زمان‌بندی و صف

## ۱) سه رویداد cron

| رویداد | تکرار ثبت‌شده | کار واقعی | قابل تنظیم؟ |
|---|---|---|---|
| `mojoodyar_process_queue` | هر ۵ دقیقه | ارسال دسته‌ای صف | اندازهٔ دسته، نرخ، بازهٔ ارسال |
| `mojoodyar_reconcile_stock` | هر ۵ دقیقه | پایش تطبیقی موجودی، **درون‌خوان داخلی شده به بازهٔ تنظیمی** | `reconcile_interval` (پیش‌فرض ۱۵ دقیقه، کف ۵، سقف ۱۴۴۰) |
| `mojoodyar_prune_records` | روزانه | حذف ردیف‌های کهنه و لاگ‌ها | `retention_days` |

**چرا reconcile هر ۵ دقیقه ثبت می‌شود اما هر ۱۵ دقیقه کار می‌کند؟**
اگر رویداد را دقیقاً روی بازهٔ تنظیمی زمان‌بندی کنیم، هر بار که مدیر بازه را
عوض کند باید رویداد را پاک و دوباره ثبت کنیم — و اگر این کار نیمه‌کاره بماند،
پایش برای همیشه خاموش می‌شود. با یک رویداد ثابت و گارد داخلی
(`Scheduler::reconcile_due()`)، تغییر تنظیمات هیچ رویدادی را دست نمی‌زند.

`Scheduler::maybe_heal()` روی هر بارگذاری ادمین بررسی می‌کند که هر سه رویداد
زمان‌بندی شده باشند؛ اگر هاست آپشن cron را پاک کرده باشد، دوباره ثبت می‌شوند.

## ۲) اجرای صف — گام به گام

```
Queue::process()
 1. acquire_lock()      ← آپشن mojoodyar_queue_lock با TTL ۳۰۰ ثانیه
    └─ اگر قفل موجود و تازه است: برگرد با skipped='locked'
 2. reclaim_stale()     ← ردیف‌های processing با locked_at قدیمی‌تر از TTL
    └─ وضعیت به queued برمی‌گردد (attempts دست‌نخورده)، رویداد queue_reclaimed
 3. بازهٔ ارسال (اختیاری، پیش‌فرض خاموش)
    └─ خارج از بازه: skipped='window' (کارها *حفظ* می‌شوند، حذف نمی‌شوند)
 4. allowance = min(batch_size, per_minute - sent_last_minute())
    └─ ≤۰: skipped='rate'
 5. SELECT ... WHERE status='queued' AND next_run_at <= now
    ORDER BY next_run_at ASC, id ASC LIMIT allowance
    └─ اگر خالی بود ولی ردیفی با next_run_at در آینده هست: skipped='scheduled'
 6. برای هر ردیف: UPDATE ... SET status='processing', locked_at=now
    WHERE id=%d AND status='queued'     ← claim اتمی؛ اگر ۰ ردیف، رد شو
 7. deliver(id): کانال را صدا بزن
 8. موفق → sent / ناموفق → attempts++ با backoff
 9. budget_exhausted(): اگر از TIME_BUDGET گذشته، حلقه را بشکن
10. release_lock()
```

گام ۲ از ۲.۶.۰ اضافه شد. پیش از آن، ثابت `QueuePolicy::LOCK_TTL` تعریف شده
بود ولی هیچ‌جا استفاده نمی‌شد: قفلِ *گزینه* با TTL آزاد می‌شد، اما ردیف‌هایی
که یک اجرای مرده در وضعیت `processing` رها کرده بود تا ابد همان‌جا می‌ماندند،
چون گام ۵ فقط `status='queued'` را می‌خواند. نتیجه یک فروشگاه واقعی: صف
همیشه «خالی» گزارش می‌شد و پیامکِ بازگشت موجودی هرگز نمی‌رفت. مهلت ۳۰۰ ثانیه
سخاوتمندانه است چون هر ارسال یک درخواست HTTP با تایم‌اوت ۱۵ ثانیه است و کل
اجرا هم با `TIME_BUDGET` محدود می‌شود؛ هیچ اجرای سالمی پنج دقیقه یک ردیف را
نگاه نمی‌دارد.

نکتهٔ مهم: گام ۵ با `AND status='queued'` انجام می‌شود. اگر دو فرآیند
هم‌زمان (مثلاً cron + اجرای دستی مدیر) وارد شوند، یکی از آن‌ها صفر ردیف
به‌روز می‌کند و همان ردیف را رد می‌کند. قفل گزینه لایهٔ اول است؛ این
`UPDATE` شرطی لایهٔ دوم.

## ۳) عقب‌نشینی (backoff)

`Logic\QueuePolicy::BACKOFF_MINUTES = [15, 60, 360]`

| تلاش | نتیجهٔ ناموفق | زمان تلاش بعدی |
|---|---|---|
| ۱ | `attempts=1` | +۱۵ دقیقه |
| ۲ | `attempts=2` | +۱ ساعت |
| ۳ | `attempts=3` | +۶ ساعت |
| ۴ | — | `status='failed'` (پس از `max_attempts`) |

`max_attempts` قابل تنظیم است (پیش‌فرض ۳). ردیف `failed` در پنل با
دلیل خطا دیده می‌شود و با ابزار «تلاش دوباره» قابل بازگردانی است.

ردیف‌هایی که باید رد شوند (`skipped`)، backoff نمی‌گیرند چون تلاش دوباره
بی‌معنی است:

- `unsubscribed` — کاربر لغو کرده؛
- `not_confirmed` — تأیید دومرحله‌ای انجام نشده؛
- `channel_disabled` — کانال در تنظیمات خاموش شده.

## ۴) پایش تطبیقی — چرا لازم است

هوک‌های ووکامرس فقط وقتی شلیک می‌شوند که تغییر از API ووکامرس عبور کند.
در عمل، موجودی در فروشگاه‌های ایرانی از راه‌های زیر عوض می‌شود:

- درون‌ریزی CSV افزونهٔ WP All Import (به‌روزرسانی مستقیم متا)؛
- همگام‌سازی ERP/انبار که با `UPDATE wp_postmeta` می‌نویسد؛
- اسکریپت دستی یا SQL روی phpMyAdmin.

هیچ‌کدام از این‌ها `woocommerce_product_set_stock_status` را صدا نمی‌زند.
پایش تطبیقی این شکاف را می‌بندد.

### الگوریتم

```
if !reconcile_due(last_run, now) → خروج
first_run = (option mojoodyar_snapshot_seeded !== 'yes')
برای هر صفحهٔ ۵۰تایی محصول (wc_get_products):
    diff = Reconcile::diff(snapshot_old, current, first_run)
    اگر گذار «ناموجود → موجود» بود:
        announce(product, variation, qty)
    snapshot_put(...)
if first_run:
    mojoodyar_snapshot_seeded = 'yes'   ← هیچ اعلانی در اجرای اول
```

### اجرای اول: فقط عکس‌برداری

روز نصب، افزونه هیچ اعلانی نمی‌فرستد، حتی اگر صد محصول «تازه موجود شده»
به‌نظر برسند، چون snapshot خالی است و هر چیزی «گذار» به‌حساب می‌آید.
`Activator::activate()` نیز همان عکس‌برداری را انجام می‌دهد
(`rebuild_snapshots()` + `snapshot_seeded=yes`).

### سقف پیمایش

حداکثر ۲۰۰ صفحه × ۵۰ = ۱۰٬۰۰۰ محصول در هر اجرا. فروشگاه‌های بزرگ‌تر از این،
در اجرای بعدی ادامه می‌یابند (صفحه‌بندی از ابتدا شروع می‌شود، پس پوشش کامل
است، فقط در چند اجرا). این انتخاب آگاهانه است تا یک هاست اشتراکی با
`max_execution_time=30` هرگز timeout ندهد.

## ۵) رفتار در شرایط سخت

| وضعیت | رفتار |
|---|---|
| `DISABLE_WP_CRON` روشن و cron واقعی تنظیم نشده | صف پر می‌شود، ارسالی انجام نمی‌شود. در داشبورد هشدار نمایش داده می‌شود؛ در راهنما روش cron واقعی توضیح داده شده است. |
| هاست کند / ارسال کند | `TIME_BUDGET` حلقه را می‌شکند، قفل آزاد می‌شود، بقیه در اجرای بعد. |
| دو اجرای هم‌زمان | قفل گزینه + `UPDATE ... WHERE status='queued'` |
| فرآیند در میانهٔ کار کشته شود | ردیف‌ها با `status='processing'` و `locked_at` قدیمی می‌مانند؛ قفل با TTL آزاد می‌شود و ردیف‌های `processing` که `locked_at` آن‌ها از TTL گذشته، در اجرای بعد بازپس گرفته می‌شوند. |
| تغییر بازهٔ ارسال وسط کار | دستهٔ جاری تمام می‌شود؛ دستهٔ بعدی در بازهٔ جدید. |
| تغییر ساعت سایت | `Queue::site_hour()` از `wp_timezone()` می‌خواند، نه `date()` سرور. |

## ۶) چه چیزی اندازه‌گیری نشد

- رفتار واقعی روی هاستی که WP-Cron را با تأخیر زیاد (یا با `wp-cron.php`
  مسدود) اجرا می‌کند. منطق در برابر تأخیر مقاوم است (پنجرهٔ `next_run_at`)،
  اما تأخیر واقعی اندازه‌گیری نشده است.
- اجرای هم‌زمان دو صف روی MySQL واقعی (تست‌های موجود روی SQLite هستند).
- پایش ۱۰٬۰۰۰ محصول واقعی: عدد ۲۰۰ صفحه سقف طراحی است، نه نتیجهٔ بنچمارک.
